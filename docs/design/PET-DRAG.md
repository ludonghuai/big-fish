## 二、设计层

### 2.1 方案选型对比

判据取自需求层：NFR-1（跟手度与开销）、NFR-2（停止与状态清空）、NFR-3（兼容性）、NFR-4（可维护性）、US-5 / US-6 / US-7（不回退）。

| # | 候选方案 | 结论 |
|---|---|---|
| 1 | 主进程按全局光标绝对定位的跟随循环 | **选定** |
| 2 | 系统原生拖动（`-webkit-app-region: drag` 或 Win32 `WM_NCLBUTTONDOWN` + `HTCAPTION`） | 否决 |
| 3 | 原生全局输入模块（`GetAsyncKeyState` 轮询按键状态）+ 主进程跟随循环 | 否决 |
| 4 | 最小改动：保留渲染层增量位移（`screenX/screenY` → IPC → 起点 + 位移），只修穿透与 `getSize` | 否决 |

#### 候选 1 — 主进程按全局光标绝对定位的跟随循环（选定）

- **跟手度**：每 ≤8ms 由全局光标直接推导，无 IPC 往返、无逐事件同步 `getSize`（对 NFR-1）。
- **停止与清空**：渲染层 `pointerup` 为主 + 1.8s 看门狗兜底（对 NFR-2）。
- **兼容**：三平台共有 API，无平台分支（对 NFR-3）。
- **可维护**：推导逻辑集中在单一函数（对 NFR-4）。
- **不回退**：窗口仍是普通窗口，click / contextmenu 正常送达；贴墙与尺寸分支原样保留（对 US-5 / US-6 / US-7 / US-8）。
- **取舍（选定的代价）**：主进程新增一个 8ms 循环（AC9 需实测 CPU）；拖动结束依赖渲染层事件送达，故需心跳 + 看门狗兜底（§2.2.6）。

#### 候选 2 — 系统原生拖动（否决）

- **跟手度**：理论最优——由 OS 进入模态移动循环，位置更新不经 JS。
- 否决 ①：模态循环期间渲染层收不到鼠标消息，click / contextmenu 被吞 → **US-5、US-6（AC5/AC6）必然回退**。
- 否决 ②：透明窗口 + 穿透 + 模态拖动组合在 Electron 下有已知重绘漂移（拖动中内容抖动 / 残影）。
- 否决 ③：位置在模态循环内无法逐帧查询 → AC3「松手即停」与 AC7 贴墙判定失去可靠时点。
- 否决 ④：Win32 路线需原生依赖（`SetWindowLongPtr` / `WM_NCHITTEST` 钩子），与 NFR-4「不新增依赖」冲突，并带来 ABI 与打包成本。
- 与批次档 §1.4 的既有技术裁定一致。

#### 候选 3 — 原生全局输入模块（否决）

- **跟手度**：与候选 1 同级（同样是主进程循环）。
- 否决 ①：需引入原生模块（node-gyp / 预编译 ABI），与 NFR-4 冲突。
- 否决 ②：它唯一解决的问题是「判断按键是否仍按下」，而该判断本设计已有三层更轻的兜底（§2.2.6）。
- 否决 ③：三平台需三套实现，收益不抵成本。

#### 候选 4 — 最小改动（否决）

- **跟手度**：① 每帧一次 IPC 往返（renderer → main → `setPosition`）；② 事件源仍是「窗口内的鼠标消息」，光标出窗即停发（根因 C 未解决）；③ 主进程同步 `getSize` 仍随事件频率排队（根因 B 残留）。
- 结论：无法满足 NFR-1 与 US-2。

### 2.2 架构与契约

#### 2.2.1 职责边界

| 侧 | 负责 | 不负责 |
|---|---|---|
| renderer（`pet.js`） | 识别拖动起止（`pointerdown` / `pointerup` / `pointercancel` / `lostpointercapture`）；区分点击与拖动（屏幕坐标位移 > 5px，沿用既有阈值）；拖动期间禁止切换穿透；心跳保活；拖动结束后重算命中并恢复动态穿透 | 不计算窗口位置（不再上报坐标）；不判断贴墙与否 |
| main（`main.js`） | 拖动期间按全局光标绝对定位驱动窗口；尺寸回拉；穿透开启请求的守卫；看门狗；散步抑制；拖动结束后的边缘挣脱分支 | 不判断点击 / 拖动语义（沿用渲染层判定）；不改散步与睡眠节奏 |

#### 2.2.2 IPC 契约

| 通道 | 方向 | 载荷 | 时点 |
|---|---|---|---|
| `pet-drag-start` | renderer → main | 无（原 `{x, y}` 取消） | `pointerdown` |
| `pet-drag-heartbeat` | renderer → main | 无 | 拖动期间每 500ms（定时器驱动，与鼠标事件无关） |
| `pet-drag-end` | renderer → main | 无 | `pointerup` / `pointercancel` / `lostpointercapture` |
| `pet-drag-cancel` | main → renderer | 无 | 主进程兜底终止拖动后，通知渲染层清标志 |
| `pet-clicked` · `pet-right-clicked` · `pet-set-ignore-mouse` · `pet-say` · `pet-state` · `pet-affinity` | 双向不变 | 不变 | 不变 |
| ~~`pet-drag-move`~~ | — | **删除** | 新机制不再需要渲染层上报坐标 |

#### 2.2.3 跟随算法

- 拖动开始时记抓取偏移：`grabOffset = cursorAtStart − windowPosAtStart`（整点差）。
- 每个 tick：`cursor = screen.getCursorScreenPoint()` → `target = (round(cursor.x − grabOffset.x), round(cursor.y − grabOffset.y))`；**仅当 `target` 与上次写入值不同**时才 `petWindow.setPosition(target)`（同目标去重，满足 NFR-1 的空闲判据）。
- **不做工作区钳制**（与现状一致，满足 US-2 边界：允许一部分拖到屏幕外）。
- 单位：`screen.getCursorScreenPoint()` 明确返回 DIP（`node_modules/electron/electron.d.ts:10862`），与 `setPosition` / `getPosition` 同一坐标系——不手写 dsf 换算。

**不变量 I1（本机制的核心论证）**：只要跟随生效，光标相对窗口的位置恒等于抓取点，即光标始终落在窗口矩形内——因为窗口位置由光标位置减去一个常量得出。因此 AC2 所描述的「光标移出窗口矩形」是跟随失效时的**症状**，而非独立问题；机制修好后该症状消失，鼠标消息不再断流，`pointerup` 得以正常送达。I1 使拖动结束检测不必依赖 OS 级捕获，事件捕获只作纵深防御（DD-3）。

#### 2.2.4 状态与生命周期

| 侧 | 载体 | 结构 | 设置点 | 清空点 |
|---|---|---|---|---|
| main | `petDrag`（模块级变量，`null` = 未在拖动） | `{ grabOffset, timer, lastApplied, sizeCheckCounter, lastMessageAt }` | `pet-drag-start` 处理器（先停旧再建新，幂等） | `pet-drag-end`；看门狗超时；窗口销毁（`destroyPetWindow`）；应用退出 |
| renderer | `dragging`（布尔） | — | `pointerdown`；伪取消后的**对称自愈重新起拖**（见 §2.2.4.1） | `pointerup`；`pointercancel`；`lostpointercapture`；收到 `pet-drag-cancel`；`pointermove` 且 `e.buttons === 0`（自愈） |

「点击 / 拖动」判定沿用既有语义：起点 `screenX/screenY` 与松开时的差 > 5px 判为拖动（`pet.js:66`）。**必须用屏幕坐标**——拖动期间窗口跟着光标走，`clientX/clientY` 近似恒定，用它判位移会永远判成点击。

#### 2.2.4.1 伪取消的对称自愈（清空点的反向路径）

渲染层的清空点中，`pointercancel` / `lostpointercapture` / `pet-drag-cancel` 三类属**伪取消**——它们可能在用户**仍按住**按键时发生（例如系统级指针捕获丢失）。若自愈只覆盖 `buttons === 0` 这一向，一次伪取消就会让**本次按住期间**彻底不再跟手（正是本批要修的现象）。故补一条对称规则：

- **重新起拖条件**：`pointermove` 事件、`e.buttons !== 0`（仍有键按下）、`dragging === false`、命中点落在窗口矩形内（`isInteractivePoint(e.clientX, e.clientY)`，`pet.js:102-110`）同时成立 → 走**与 `pointerdown` 完全相同的起拖入口**（同一函数：置 `dragging = true`、`moved = false`、`startX/startY = e.screenX/screenY`、重新获取指针捕获、重启渲染层心跳、发 `pet-drag-start`）。
- **与「位移 > 5px 判拖动」阈值如何共存**：重新起拖把判定原点重置为**当时的屏幕坐标**，位移自重新起拖点起重新累计；阈值语义不变（仍 > 5px 判拖动）。若伪取消后用户只是轻微抖动（累计 ≤ 5px），本次按住不产生拖动语义，松手仍走点击路径（US-5 不回退）。
- **不产生位置跳变**：主进程每次收到 `pet-drag-start` 都以**当时的**光标与窗口位置重算 `grabOffset`（§2.2.3），故重新起拖不会让窗口瞬移——手感连续。
- **不可达的边角（如实标注）**：伪取消瞬间若光标恰在窗口矩形之外，该 `pointermove` 不会送达渲染层，重新起拖在此瞬态下不触发；待光标回到矩形内（I1 下的常态）或用户松开后重新按下即恢复。

#### 2.2.5 跟随循环的启停条件

- **启动**：收到 `pet-drag-start`（= 按下瞬间，与现状同刻）。纯点击场景下 `target` 恒等于原位置，不产生任何位移，故不影响 US-5。
- **tick 内自终止**：`petWindow` 不存在或已销毁。
- **停止**：`pet-drag-end`（停止前做一次最终位置同步 + 尺寸回拉）；看门狗超时；窗口销毁。

#### 2.2.6 心跳与超时（兜底）

常量：`PET_DRAG_TICK_MS = 8`（标称）、`PET_DRAG_SIZE_CHECK_TICKS = 8`、`PET_DRAG_KEEPALIVE_MS = 500`（渲染层）、`PET_DRAG_STALE_MS = 1800`（主进程）、`PET_DRAG_PROBE_MS = 250`（日志探针，见 §3.3）。

- 心跳由渲染层**定时器**驱动，与鼠标事件无关——长按不动（AC4）期间事件为零但心跳照发，**不会被误判为失联**（这是心跳必须由定时器而非事件驱动的原因）。
- 主进程每个 tick 检查 `Date.now() − lastMessageAt > PET_DRAG_STALE_MS` → 调 `petStopDrag('stale')` 并发 `pet-drag-cancel` 给渲染层清标志。
- 另在 `petWindow.webContents` 的 `render-process-gone` 与窗口 `closed` 路径终止拖动。
- 阈值取值的依据：500ms 心跳 + 1800ms 超时 = 容忍连丢 3 拍；且 1800ms < NFR-2「最迟 ≤2s 清空」的 2s 上限，留 200ms 余量以吸收 tick 粒度与调度抖动（若取 2000ms，叠加 tick 粒度后实际会略超 2s）。
- `PET_DRAG_TICK_MS = 8` 的**口径**：标称周期（≈125Hz）。JS 定时器粒度只会 ≥ 8ms，故允许 +2ms 内偏差（实测平均周期 ≤ 10ms）；实测手段见 §3.3 第 5 条。

#### 2.2.7 穿透策略（根因 A）

- 渲染层：拖动期间，命中判定的 `mousemove` 处理器与 `mouseleave` 处理器直接 return，不切换穿透（现状 `pet.js:111-124` 无此守卫）。
- 渲染层：`pointerdown` 时若渲染层自认为处于穿透态，先请求 `setIgnoreMouse(false)`，保证拖动期间窗口可收事件。**该分支的可达条件（避免死分支）**：渲染层发出的「开启穿透」是异步 IPC（`pet-set-ignore-mouse`），在主进程应用之前的窗口期内、或主进程依本节守卫忽略该请求时，渲染层认为窗口处于穿透态而窗口实际仍能收事件——此时 `pointerdown` 可送达；穿透已生效的稳态下 `pointerdown` 不送达渲染层，故本句只是该窗口期的防守，不构成拖动起点所依赖的路径。
- 主进程（防守）：`pet-set-ignore-mouse` 处理器在 `petDrag !== null` 时忽略「开启穿透」的请求。
- 拖动结束：渲染层用 `pointerup` 事件的 `clientX/clientY` 重算命中并应用 `setIgnoreMouse(!interactive)`，恢复既有的动态穿透。
- 穿透的 win32 专属判定（`pet.js:97-98`、`main.js:1787`）**原样保留**，不新增平台分支。

#### 2.2.8 散步抑制（根因 D）

- `pet-drag-start`：保留既有 `clearInterval(moveTimer)`（`main.js:1733`），并把既有的 `scheduleWander()`（`main.js:1736`）改为 `clearTimeout(wanderTimer); wanderTimer = null;`——现状这一句恰恰是在拖动开始时**安排**了一次 15~35s 后的散步，是根因 D 的直接来源。
- `doWander()` 守卫（`main.js:667`）增加 `petDrag !== null` 判据：任何来源的散步都不会在拖动中移动窗口（覆盖「拖动开始前就已挂起的定时器」）。
- `pet-drag-end`：非贴墙分支仍调 `scheduleWander()`（`main.js:1765`）；贴墙分支仍调 `doWander()`（`main.js:1763`）。

#### 2.2.9 尺寸回拉（US-8）

- 抽出 helper `fixPetWindowSize()`：`getSize()` 不符则 `setSize(250, 270)`。
- 调用点：① 拖动循环内每 `PET_DRAG_SIZE_CHECK_TICKS`（8）个 tick 一次（≈64ms，约 16 次/秒）；② 拖动结束时一次；③ 散步循环的既有回拉调用点（`main.js:702-704`）**改为调用 `fixPetWindowSize()`**——该处原为内联的重复实现（`main.js:703-704`，与拖动路径重复），本批只把实现换成 helper 调用，**调用频率（每 tick 一次）与语义均不变**（消除重复实现，承载 NFR-4）。
- 语义不变（US-8 边界）：仍是「发现漂移即拉回」，拖动路径只降低调用频率以服务 NFR-1。
- **口径澄清（对 NFR-1「单次推导内不得包含同步的窗口尺寸查询」）**：该判据约束的是**推导步骤**（`光标 → target` 的换算，§2.2.3）；尺寸回拉是与之分离的独立检查——不在推导内、不参与 target 计算，且拖动路径上已无**逐事件**查询（既有逐事件查询在 `main.js:1747-1748`，本批随 `pet-drag-move` 通道一并删除）。故 NFR-1 条文本批不作改动。

#### 2.2.10 拖动结束与贴墙挣脱（US-7）

`pet-drag-end` 后：`clearInterval` 跟随循环 → 最终位置同步 → 尺寸回拉 → 位置判定 `x <= 4 || x >= petMaxX() − 4` 时走既有挣脱分支（`main.js:1754-1763`，原样保留），否则 `scheduleWander()`。

### 3.3 验证手段、仪表与限制

**验证手段**

1. **诊断日志（本批唯一机器取证手段）**：env `BIGFISH_PET_DEBUG=1` 时开启，默认关闭（关闭时零开销）。写入 `userData/pet-drag.log`，`appendFileSync` + `try/catch` 尽力而为（先例：`exchange.log`，`main.js:896-901`）。
   采样行（每 16 tick ≈128ms 采样一行，仅拖动期间）：
   `[ISO 时间] tick cursor=(x,y) target=(x,y) applied=(x,y) delta=(dx,dy) off=(dx,dy) wrote=0|1 size=(w,h)`
   列义：
   - `delta = target − applied`——证明该 tick 的 `setPosition` 目标已生效；
   - `off = cursor − (applied + grabOffset)`——NFR-1「光标 ↔ 被抓住的那一点偏移 ≤ 2px」的**直接度量**（`applied` = 窗口当前位置，`grabOffset` = 本次拖动的抓取偏移；跟随无误差时 `off = (0,0)`）；
   - `wrote = 1` = 该 tick 实际调用了 `petWindow.setPosition()`（经同目标去重），`wrote = 0` = 未写入——AC3 / AC4 按「`wrote=1` 的行」计数；
   - `size=(w,h)` = 该采样时刻的窗口尺寸（供 AC8）。
   生命周期行：
   `[ISO 时间] drag-start grabOffset=(dx,dy) pos=(x,y)`；
   `[ISO 时间] drag-end reason=<pointerup|pointercancel|lostcapture|stale|destroyed> pos=(x,y) size=(w,h)`（`size` = 拖动结束时刻的实测尺寸——AC8 关心的正是该时刻）；
   `[ISO 时间] probe pos=(x,y) size=(w,h)`——`drag-end` 后 `PET_DRAG_PROBE_MS`（250ms > NFR-2 的 200ms 上限）追加一条**静态探针行**，使 AC3 可伪证（否则「drag-end 之后不再有位置行」因「位置行只在拖动期间写入」而结构性恒真）；`reason=destroyed`（窗口已销毁，`getPosition()` 不可用）时跳过该行，并在 `drag-end` 行注明。
   `applied` 由 `petWindow.getPosition()` 读取（仅在日志开启时采样，避免常态开销）。
2. **手工验证清单**：按 §3.2 逐条执行并记录结果（含 AC5–AC8 的回归项）。
3. **静态核对**：改动后核对「拖动路径上不再出现**逐事件**的同步 `getSize()`（根因 B；拖动循环的尺寸检查已收敛为 `fixPetWindowSize()`、每 8 tick 一次——口径见 §2.2.9）」「拖动路径不再出现 `setIgnoreMouseEvents(true)`」「窗口自主位移的唯一来源（散步循环 `doWander` / `moveTimer`）在拖动态被守卫覆盖」。
4. **语法门**：`node --check main.js`、`node --check pet.js`、`node --check pet-preload.js`（本仓无 lint / test script，此为可用的最小机械门）。
5. **跟随周期分布实测**：取日志相邻采样行的时间戳差 ÷ 16 得平均 tick 周期——标称 `PET_DRAG_TICK_MS = 8`，允许 +2ms 内偏差（平均周期 ≤ 10ms，口径见 §2.2.6）。

**只能人工验证的条目（如实标注）**
