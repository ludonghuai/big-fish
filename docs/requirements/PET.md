# 桌宠（鲸鱼娘）需求档 — PET

> 归属板块：桌宠（桌面挂件）
> 落点：`docs/requirements/PET.md`（本档为桌宠需求唯一权威源）
> 关联批次：`docs/batches/B01-pet-drag-follow.md`
> 关联设计档：`docs/design/PET-DRAG.md`（设计档回指本档条目 US-1…US-8、NFR-1…NFR-4）

---

## 一、总目标

让使用桌面端（本批验收目标平台为 Windows）的用户在拖动桌宠「鲸鱼娘」时，窗口与鼠标光标严格同步、完全跟手、无可感延迟，同时不牺牲任何既有交互。

---

## 二、范围

本档当前登记的，是**桌宠拖拽跟手**这一交互的需求（B01 批次），以及与之相邻、本批不得回退的既有交互约束。

明确不包含（本批不做，本档也不为其补造需求条文）：

- 多显示器下的几何策略（散步边界、贴墙判定口径）的重新设计；
- macOS / Linux 的专项验证——只要求不回退既有行为；
- 桌宠其余机制（好感度、兑换屋、散步、睡眠、闲聊）的功能性需求——它们目前只存在于代码中，本档不代其立需求；
- 「右键手势同时触发唤起主窗口」这一既有行为的修正（属既有语义缺口，见设计档观察项 F2，需用户裁决是否另批处理）。

## 三、功能用户故事

格式：**作为一个 [角色]，我想要 [功能]，以便 [目的]**。
每条以「验收」标注对应验收条目——编号取自 `docs/batches/B01-pet-drag-follow.md` §1.5（AC1…AC9，已由用户确认）。

### US-1 拖动跟手（验收：AC1）

作为一个使用桌宠的用户，我想要在按住鲸鱼娘移动时她与光标保持严格同步（无可感滞后、无脱离），以便获得与拖动原生窗口一致的拖拽手感。

- 边界（不做）：不做拖拽惯性、缓动、吸附等后置修饰——任何后置动画都与「跟手」直接冲突。

### US-2 拖出窗口矩形仍跟随（验收：AC2）

作为一个使用桌宠的用户，我想要在拖动过程中把光标移出桌宠窗口矩形（含一路拖到屏幕边缘）时她仍持续跟随，以便大幅拖动不会中途掉队或停住。

- 边界（不做）：不把窗口位置钳制在屏幕工作区内（允许一部分拖到屏幕外），与现状保持一致。

### US-3 松手即停且不粘连（验收：AC3）

作为一个使用桌宠的用户，我想要在松开鼠标后她立刻静止、且拖动状态一定被清空，以便随后的点击与拖动都能正常响应。

- 边界（不做）：不引入「松手惯性滑行」。

### US-4 拖动期间不被自主走动打断（验收：AC4）

作为一个使用桌宠的用户，我想要在长时间按住她不动时她不会自己走开，以便整个拖动过程完全由我控制。

- 边界（不做）：不顺带改动散步 / 睡眠 / 闲聊的既有触发节奏（非拖动期间行为保持现状）。

### US-5 原地点击仍唤起主窗口（验收：AC5；不得回退）

作为一个使用桌宠的用户，我想要在不产生位移的原地点击后仍然弹出主窗口并播放开心动画，以便点击唤起功能保持可用。

- 边界（不做）：不改动点击判定阈值（位移 > 5px 判为拖动）与主窗口显隐语义。

### US-6 右键仍打开兑换屋（验收：AC6；不得回退）

作为一个使用桌宠的用户，我想要右键点击时仍然打开兑换屋窗口，以便兑换功能保持可用。

- 边界（不做）：不改动兑换屋窗口的定位策略（其跟随鲸鱼娘当前位置的既有逻辑保持原样）。

### US-7 拖到边缘松手仍挣脱逃跑（验收：AC7；不得回退）

作为一个使用桌宠的用户，我想要把她拖到屏幕左右边缘松手时仍触发「挣脱逃跑」反应，以便这一既有彩蛋行为保持可用。

- 边界（不做）：不改动逃脱的触发阈值（距边缘 4px）与逃跑动作本身。

### US-8 拖动后尺寸不漂移（验收：AC8；不得回退）

作为一个使用桌宠的用户，我想要拖动结束后窗口仍保持 250×270（不出现尺寸回拉造成的视觉跳动），以便桌宠尺寸稳定。

- 边界（不做）：不删除既有的尺寸回拉 workaround，只调整其调用方式与频率。

## 四、非功能标准

### NFR-1 性能（跟手度与开销；验收：AC1、AC9）

- **推导方式**：窗口位置必须由「光标当前位置」直接推导（绝对定位），推导周期 ≤ 8ms（约 125Hz），且单次推导内不得包含同步的窗口尺寸查询。
- **跟手判据**：拖动过程中，「光标」与「鲸鱼娘被抓住的那一点」之间的相对偏移恒 ≤ 2px；需覆盖慢拖、快拖、大幅甩动三种情况。
- **开销判据**：拖动期间主进程 CPU 增幅 < 5%。度量方式：`process.getCPUUsage()`（Electron 主进程 API，见 `node_modules/electron/electron.d.ts:24153`）；基线取拖动前 10s 空闲均值，采样为连续拖动 10s 的均值。
- **空闲判据**：光标不动时，拖动循环不得产生窗口位置写入（同目标位置去重）。

### NFR-2 可用性（停止与状态清空；验收：AC3）

- 松手后 ≤ 200ms 内窗口必须静止。
- 拖动状态在所有路径下都必须被清空，最迟 ≤ 2s——包括事件丢失、渲染进程异常、窗口销毁等异常路径。
- 度量方式：诊断日志（格式见设计档 §3.3）中 `drag-end` 行之后不得再出现位置写入行；异常路径下 `drag-end` 行的 `reason` 必须取兜底值。

### NFR-3 兼容性

- **核心机制平台无关**：只使用 Electron 三平台共有 API，代码中不得出现平台分支——既有的「穿透开关仅 win32 生效」分支除外，其保持原样。
- Windows 为验收与验证目标平台。
- macOS / Linux 既有行为不得回退。度量方式：改动仅涉及跨平台 API 与既有 win32 分支；评审时逐条核对设计档 §2.3 的改动点表。

### NFR-4 可维护性

- 位移推导集中在单一函数内；「尺寸回拉」这一 Windows workaround 收敛为单一 helper（消除重复实现）。
- 新增状态标志必须有明确生命周期——设置点与清空点成对出现，且异常路径也清空。
- 不新增第三方依赖、不新增原生模块：`package.json` 的 `dependencies` / `devDependencies` 保持不变。
