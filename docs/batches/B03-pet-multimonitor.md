### 1.2 任务来源（用户原话）

> 「为什么我这边三个屏幕，把大鲸鱼放在屏幕交换处，会丢失桌宠？或者我把它放的太靠下了，也会丢失，我不知道具体的问题定位，但是先帮我解决一下丢失问题」

> 「1、重启项目后桌宠回来了；2、切换模式之后回来了；3、我有点不太知道了，我刚刚把它拖出边界的话是没有设计边框限制的，不是静止突然消失，是交互过程结束时候；主屏是中间这个，左右都是拓展屏幕，鼠标拖动跨屏的时候，鼠标与大鲸鱼错位问题能解决吗？只是显示错位了而已」

> 「而且大鲸鱼从屏幕跑过来到小屏幕的时候，会变小，而且鼠标再拖动会变大，你也要同时解决这个问题；缩放问题得适配每个用户呀，不可能让每个人屏幕缩放比都不一样；对，中心点给它拉回来；同批做了」

### 1.3 已确认的需求结论

1. **桌宠可跨三屏活动**：移动边界按「桌宠当前所在那块显示器」的工作区计算，而非全局或主屏口径。
2. **松手做可见性校正**（用户原话「中心点给它拉回来」）：拖动结束时，若桌宠窗口中心点不落在任何显示器的工作区内，把它拉回最近可见位置。
3. **混合 DPI 适配**（用户原话「缩放问题得适配每个用户呀，不可能让每个人屏幕缩放比都不一样」）：各显示器缩放比不同时，桌宠在任一块屏上的视觉大小必须一致；不得依赖用户把各屏缩放设成同一值。
4. **跨屏拖动错位一并修**（用户原话「只是显示错位了而已」）：拖动跨屏时光标与桌宠不得错位。
5. **位置持久化同批做**（用户原话「同批做了」）：记住上次位置；显示器配置变化（如拔掉副屏）后自动回落到可见区。
6. **找回入口**：托盘提供「找回桌宠」入口（主 agent 建议、用户未反对，按纳入处理）——即使几何再出意外，用户可一键拉回。

### 1.4 主 agent 已确证的根因（亲读代码，供设计者免于重复探索）

**用户的三个回答已锁定故障链**：重启/切模式能找回 ⇒ 窗口未销毁、只是处在**无显示器覆盖的坐标**；「交互过程结束时」消失、拖动本身无边界限制 ⇒ 指向**松手后的处理**。

| # | 根因 | 证据 |
|---|---|---|
| 1 | **边界只按主显示器算**：`petMaxX()` 返回「主屏工作区宽度 − 250」，被当作全局右边界 | `main.js:757-759` |
| 2 | **y 坐标从不校验**：散步与跟随写入位置时 y 恒为原值，从无钳制 | `main.js:803`（`setPosition(nx, y)`）；`main.js:660`、`main.js:691` 同样只算 x/y 目标但无可见性校验 |
| 3 | **贴墙判定用错误基准 ⇒ 任何副屏都被误判为「贴墙」**：`x <= 4 \|\| x >= maxX - 4` 中的 `maxX` 是主屏口径 | `main.js:1860-1862`（配合 `main.js:757-759`） |
| 4 | **无任何找回手段**：窗口创建时不设位置、不做位置持久化，托盘无「找回桌宠」入口 | `main.js:559-576`（建窗无坐标）；全仓 grep 无找回入口 |
| 5 | **写死的 DIP 尺寸在混合 DPI 下必然出错**：`fixPetWindowSize()` 强制 `setSize(250, 270)`（DIP 值），且拖动跟随循环每 8 tick 调用一次 | `main.js:642-646`（helper）、`main.js:696`（每 8 tick 调用） |

**现象与根因的对应**（用户报告 → 代码机制）：

| 用户现象 | 机制 |
|---|---|
| 拖到**屏幕交界处**丢失 | 副屏松手 → `x <= 4 \|\| x >= maxX - 4` 误判贴墙 → 触发挣脱逃跑 → 按主屏口径反转方向并钳制 x，y 保持副屏值 → 落在屏幕之间的无显示器区域 |
| 放到**太靠下**丢失 | 拖动不限制边界（设计如此）→ y 超出工作区后，散步/逃跑只改 x、从不改 y → 纵向不可见 |
| 从**大屏跑到小屏变小**，**一拖动又变大** | `fixPetWindowSize()` 的 `250×270` 是 DIP 值；跨混合 DPI 显示器时 DIP↔物理换算基准改变，窗口物理尺寸与视觉大小随之跳变（拖动时每 8 tick 强制拉回 ⇒ 立即跳变） |
| 跨屏拖动**光标与桌宠错位** | 疑似同一 DPI 根因：`screen.getCursorScreenPoint()` 与 `setPosition()` 的 DIP 基准在跨屏处不一致 |

> **待查证（不得凭记忆定方案）**：上表后两行的 Electron 跨屏 DIP 换算具体行为，主 agent 系由现象反推，**未经 electron 文档/类型定义验证**。设计者须以 `node_modules/electron/electron.d.ts` 与官方文档为准核实后，方可定方案。

| # | 标准 | 判定方式 |

### 1.6 既有实现约束（设计不得违反）

- 桌宠窗口固定 250×270（DIP）、透明、无边框、`alwaysOnTop('floating')`、`skipTaskbar`、`resizable:false`（`main.js:559-576`）。
- 散步只沿 x 轴移动，y 恒定（`main.js:803`）——本批是否允许 y 变化须在设计档明确。
- 尺寸回拉 `fixPetWindowSize()` 是既有的 Windows 漂移 workaround，不得简单删除，须改为 DPI 感知。
- 拖动跟随机制（B01）用 `screen.getCursorScreenPoint()` 绝对定位（`main.js:687-691`），本批改动须与它兼容、不得回退其跟手性。
- 贴墙挣脱是既有产品行为（`main.js:1860-1872`），须保留（但基准改为所在屏）。
- 穿透开关仅 win32 生效（`pet.js`），不得新增平台分支（承 B01 的 NFR-3 口径）。
