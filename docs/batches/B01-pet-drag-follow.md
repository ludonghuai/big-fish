### 1.2 任务来源（用户原话）

> 「现在有一个明显的问题，就是鼠标拖动小鲸鱼的时候，小鲸鱼跟不上，怎么解决呢？」

> 「对，修复Windows；方案选择我只要鲸鱼完全跟手，无延迟，你自己选择，不怕改动大，如果调用了外部的包你甚至可以选择自己重写一份，明白吗」

> 「可以，确认」

### 1.3 已确认的需求结论

修复 Windows 下桌宠拖拽不跟手：把拖拽移动改为主进程按**全局光标绝对定位**驱动，并消除拖动期间的事件断流、状态粘连与散步抢占。既有交互（点击唤起主窗口、右键打开兑换屋、拖到边缘松手挣脱逃跑、拖动后尺寸保险）**零回归**。

### 1.4 主 agent 的技术裁定（用户授权范围内）

用户在上一轮明确授权：「方案选择我只要鲸鱼完全跟手，无延迟，你自己选择」。据此主 agent 裁定以下两点：

1. **平台范围 = 核心机制平台无关**。新机制仅使用 `screen.getCursorScreenPoint()`（Electron 三平台共有 API），不为 macOS/Linux 另写一条旧路径——双代码路径的复杂度翻倍而收益为零。Windows 是本次的**验收与验证目标平台**；macOS/Linux 不额外承诺验证，但也不得回退既有行为。
2. **不引入原生拖动方案**。`-webkit-app-region: drag` / Win32 `WM_NCLBUTTONDOWN`+`HTCAPTION` 虽理论最跟手，但会进入系统模态循环吞掉 click 与 contextmenu，导致「点击唤起主窗口」「右键打开兑换屋」失效，且透明窗口 + 穿透 + 模态拖动组合在 Electron 下有已知重绘漂移问题。否决理由须在设计档的方案选型对比中留档。

### 1.6 已勘察的根因（主 agent 亲读代码确证，供设计者免于重复探索）

| # | 根因 | 证据位置 |
|---|---|---|
| A | 拖动中途窗口被置为「穿透」，事件流被切断：穿透判定未检查拖动状态，拖动必然使光标离开鲸鱼矩形而触发穿透，`mouseup` 随之丢失 | `main.js:580`（初始 `setIgnoreMouseEvents(true,{forward:true})`）、`pet.js:111-117` |
| B | 每个 mousemove 都做一次同步 `getSize()` 并可能 `setSize()`，高刷屏下原生调用排队追不上光标 | `main.js:1747-1748` |
| C | 没有指针捕获：窗口仅 250×270，快拖时光标出窗即停发事件，窗口停滞、`mouseup` 丢失导致状态粘连 | `pet.js:56-74` |
| D | 拖动期间散步定时器未被抑制：dragStart 中调用 `scheduleWander()`，而 `doWander` 守卫为 `petState==='idle'`，拖动中恰好满足，长按超过 15~35s 会自主抢占窗口位置 | `main.js:1736`、`main.js:667`、`main.js:1734` |

### 1.7 既有实现约束（设计不得违反）

- 拖拽起点/位移当前由 renderer 传屏幕绝对坐标，主进程按「起点 + 位移」增量计算窗口位置（`main.js:1737-1745`）。
- `pet.html` 中 `#pet` 为 `pointer-events: none`，鼠标命中依赖 `getBoundingClientRect()` 判定（`pet.js:102-110`）。
- 穿透开关 `setIgnoreMouseEvents` 仅在 win32 生效（`pet.js:97-98` 以 `navigator.platform` 判断）。
- 窗口尺寸回拉（250×270）是已知的 Windows 漂移 workaround，多处存在，不得简单删除而不给替代。
- 拖动结束的「贴墙挣脱逃跑」分支为既有产品行为（`main.js:1750-1763`），须保留。
